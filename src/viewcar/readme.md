# viewcar —— 车载 ADAS 感知可视化

基于 **OpenGL 3.3** 的自动驾驶 / ADAS 感知结果可视化工具。模拟一套 L2 级辅助驾驶系统的
**感知 + 规划 + 控制**输出，并实时三维可视化，用于观察算法在真实道路场景下的行为。

> 面向车载 HMI / ADAS 可视化方向：目标检测框、车道线、传感器视场、风险告警（TTC）、
> 自车运动学与规控轨迹。

## 三、中文字体说明

ImGui 内置字体 **ProggyClean 只包含 ASCII 字形**，如果直接使用，
界面上所有中文都会渲染成 `?`。本项目在启动时从系统字体文件加载中文字形：

```cpp
io.Fonts->AddFontFromFileTTF(path, size, &cfg, io.Fonts->GetGlyphRangesChineseFull());
```

要点：

1. **必须用 `GetGlyphRangesChineseFull()`**，不能用 `GetGlyphRangesChineseSimplifiedCommon()`。
   后者只收录约 2500 个高频字，本项目用到的「锥」「桶」「骑」「瞰」等字不在其中，
   会出现「大部分中文正常、个别字变问号」的诡异现象。
2. **按顺序尝试候选字体**，取第一个可用的：等线 → 黑体 → 微软雅黑 → 宋体 → 楷体
   （同时提供 Linux 文泉驿与 macOS 苹方路径，便于跨平台）。
3. **`OversampleH/V = 2`**：中文笔画密集，2 倍过采样显著改善小字号可读性。
4. **主面板「界面字号」滑块**：拖动即重建字体图集，无需重启程序。
5. 若全部字体都不可用，会回退到内置字体，并在面板顶部显示
   `警告: 未能加载系统字体，中文可能显示为 '?'`，避免用户误以为是渲染 Bug。

> 控制台日志同理：源码是 UTF-8，而 Windows 控制台默认 GBK 代码页，
> 所以 `main()` 里调用了 `SetConsoleOutputCP(CP_UTF8)` 修正中文输出。
> 注意 `std::locale::global()` 的 locale 名称在不同 C++ 运行时上并不通用
> （MinGW 不认 `.UTF-8`，会抛 `std::runtime_error`），因此代码中逐个尝试并捕获异常。

## 四、目标类别配色与车型约定

### 4.1 车型（网格外观）

每个类别不再是一个缩放的立方体，而是由多个零件装配出的**可辨识车型**：

| 类别 | 零件构成 | 关键辨识特征 |
|---|---|---|
| **轿车** | 三段式车身（引擎盖 / 座舱 / 后备箱）+ 悬挂玻璃带 + 侧裙 + 后视镜 + 车顶 + 4 轮 + 前后灯 | 低矮流线、座舱内缩 |
| **卡车** | 驾驶室（含导流罩 / 脚踏板 / 长支架后视镜）+ 方形货箱 + 底盘大梁 + **6 轮双联轴** | 方正高大、后轴双胎 |
| **行人** | 躯干（含肩 / 双臂）+ 头颈 + 双腿（含鞋） | 人体比例：腿 47% / 躯干 34% / 头 16% |
| **骑行者** | 自行车（前后轮 / 车架 / 车把 / 车座）+ 前倾骑手（含头盔） | 前倾骑行姿态 |
| **锥桶** | 方形底座 + **真圆锥**主体 + 反光带 | 交通锥造型 |

### 4.2 车身为「真实车漆色」

车身按目标 `id` **稳定**地取一个车漆色（同一目标每帧颜色不变，不会闪烁），
使画面接近真实车流：

| 类型 | 调色板 |
|---|---|
| 轿车 | 珍珠白 / 银灰 / 深蓝黑 / 中国红 / 深海蓝 / 石墨黑 / 香槟金 |
| 卡车 | 冷白 / 蓝灰 / 铁锈橙 / 墨绿（驾驶室用彩色，货箱统一素白） |
| 行人 | 红 / 蓝 / 绿 / 米黄 / 紫 / 深灰（上衣与裤子不同深浅） |
| 街景 | 树冠 6 种绿（分层渐变，顶部受光更亮）；楼体外墙 6 种立面配色 |

### 4.3 类别语义由包围盒承载

原本「颜色 = 类别」的编码改为由 **3D 包围盒线框颜色**承载，这样车身可以
自由使用真实车漆色，而数据语义依然清晰可读：

| 颜色 | 类别 | 典型尺寸（长 × 高 × 宽） |
|---|---|---|
| 🟢 绿 | 轿车 | 4.60 × 1.50 × 1.80 m |
| 🔵 蓝 | 卡车 | 9.00 × 3.20 × 2.50 m |
| 🟠 橙 | 行人 | 0.60 × 1.75 × 0.60 m |
| 🟡 黄 | 骑行者 | 1.80 × 1.70 × 0.70 m |
| 🔴 红 | 锥桶 | 0.40 × 0.70 × 0.40 m |

**视觉编码规则**（ADAS 界面通用语言）：

- **TTC < 3 秒**的危险目标，包围盒变为**红色高亮**
- **未被跟踪器稳定关联**的目标，车身颜色**变暗**（×0.78）表示不确定
- **预测目标**（非量测）进一步压暗（×0.72）
- 车身亮度随**置信度**线性变化（`0.62 + 0.38 × confidence`）
- **青色**表示规划量（自车规划轨迹），**橙色**表示历史量（行驶轨迹）
- **自发光**（车灯 / 路灯 / 信号灯 / 楼体窗带）由 `uEmissive` 控制，可用 `B` 或面板开关

## 七、关键技术点

### 1. 自车运动学：自行车模型

车载算法最常用的简化车辆模型，用轴距 `L` 与前轮转角 `δ` 描述运动：

```
x'     = x + v · sin(θ) · dt
z'     = z + v · cos(θ) · dt
θ'     = θ + (v / L) · tan(δ) · dt
```

对应 `EgoVehicle::update()`。坐标约定：**车头指向 +Z**，航向角以 +Z 为 0°、朝 +X 转向为正。

### 2. 横向控制：预瞄式 P 控制器

`LaneKeeper::computeSteering()` 取自车前方 `lookAheadDistance` 处的车道中心，
计算横向偏差后输出前轮转角：

```cpp
lateralError = ahead.x - laneCenterX;
steer = -lateralError * gain * speedFactor;   // 限幅 ±25°
```

其中 `speedFactor` 让低速时获得更高转向增益（低速同样转角产生的横向位移更小）。

### 3. 风险评估：TTC

`PerceptionObject::updateDerived()` 把目标位置转到**自车坐标系**（纵向 / 横向分解），
再计算接近分量得出碰撞时间：

```
TTC = distance / closingSpeed     （仅当目标在前方且正在接近）
```

TTC < 4 秒计入「风险目标」计数，TTC < 3 秒触发红色包围盒告警。

### 4. GPU 实例化与批次归并

`ShapeMesh::setupInstancing()` 把**模型矩阵（4 个 vec4）+ 颜色（vec3）**作为
逐实例属性（`glVertexAttribDivisor = 1`）绑定到专用 VAO。

在只有方块车时，「所有目标一次画完」就够了。但车型化之后，一辆轿车由
**十几个零件**组成（车身 / 玻璃 / 4 轮 + 4 轮辋 / 前后灯），如果每个零件都单独
draw，24 个目标会产生数百次 draw call。

因此新增了 **`InstanceBatch` 批次归并**机制：

```
pushPart(batches, mesh, model, color, metallic, roughness, rim, emissive)
        ↓  按「网格指针 + 材质（量化到 1/1000）+ 颜色」查找已有批次
        ↓  命中 → 追加模型矩阵；未命中 → 新建批次
flushBatches(batches)   → 每批一次 drawInstanced()
```

关键设计点：

1. **同色车自动合并**：调色板只有 7 种车漆色，因此同色轿车会落进同一批次，
   实例数很高而 draw call 很低。
2. **材质量化比较**：浮点数直接 `==` 不可靠，统一乘 1000 转 `int` 再比。
3. **颜色容差 0.004**：既允许同色合并，又不会把深浅不同的车漆混在一起。
4. **整场景 draw call 数量级**：五类目标 + 街景道具通常只需 **20~40 次**，
   与目标数量基本无关。

### 5. 线段批处理

`DebugLines` 支持每帧 `clear() → add*() → flush() → draw()`：车道线、包围盒、
FOV 锥、网格、轨迹全部合并到**一次 `glDrawArrays(GL_LINES)`**。
顶点缓冲按 2 倍余量扩容，避免频繁重分配。

### 6. 渲染顺序与状态

```
天空（不写深度，z = w 技巧 + GL_LEQUAL）
  → 路面（沥青 + 人行道 + 路缘石 + 中央分隔带，跟随自车）
    → 街景（树 / 楼 / 路灯 / 行人 / 护栏，批次实例化）
      → 自车（与轿车共用零件装配 + 前轮转向角）
        → 感知目标（按类别装配车型，批次实例化）
          → 线段层（glDepthMask(GL_FALSE)：被实体遮挡，但不互相遮挡）
            → 后处理（暗角 + 对比度，渲染缩放支持 0.5x~1.5x）
```

### 7. 无限道路与无限街景

自车前进超过 200 m 时，把**自车、所有目标与所有街景道具整体平移回起点**，
同时按自车位置重建车道线、回收后方目标与道具并向前方补充。

街景生成用的是**稳定伪随机**（`hash01(i, salt)`，整数哈希而非 `std::rand()`）：

```cpp
float hash01(int i, int salt) {
  unsigned int x = i * 374761393u + salt * 668265263u;
  x = (x ^ (x >> 13)) * 1274126177u;
  return (x ^ (x >> 16)) & 0xFFFFFFu / 16777216.0f;
}
```

这一点很关键：如果街景用 `std::rand()` 生成，那么**每次世界循环平移后，
楼房和树都会重新「长」一遍**，屏幕上会出现明显的跳变闪烁。
用位置索引做种子的哈希函数可以保证「同一坐标永远生成同一栋楼」，
于是世界平移在视觉上完全无感。

### 8. 程序化网格拼装（props.cpp）

所有车型与街景道具都是**程序化拼装**的，不加载任何外部模型文件：

| 图元 | 实现 |
|---|---|
| 盒子 | `appendBox()` — 6 个面各自 4 顶点，保证硬边法线 |
| 圆柱 | `appendCylinder()` — 侧面 + 顶盖 + 底盖，径向分段可调 |
| 圆锥 | `appendCone()` — 侧面三角扇 + 底盖（锥桶终于是锥形了） |
| 球 | `appendSphere()` — 经纬网格（树冠 / 行人头部 / 头盔 / 灌木） |

每个 `append*()` 都接收一个**局部变换矩阵**，因此可以像搭积木一样
把「引擎盖」「导流罩」「横担」「车轮」摆到正确位置：

```cpp
appendBox(v, i, partXform({0.0f, -0.10f, 0.34f}, {0.92f, 0.26f, 0.34f}));  // 引擎盖
appendCylinder(v, i, partXform({...}, {...}, 0.0f, 0.0f, 90.0f), 18);       // 车轮绕Z转90°变轴向X
```

法线在 `pushVertex()` 里用变换矩阵的 3×3 部分变换后归一化，
因此所有零件都能正确参与 `scene.frag` 的光照计算。

### 9. 自发光通道

`scene.frag` 新增 `uEmissive` uniform，在漫反射 + 环境光 + 边缘光之后叠加：

```glsl
if (uEmissive > 0.0)
    color += albedo * uEmissive;   // 加在雾之前，因此远处灯光会被雾衰减
```

用于：车头灯（近白）、尾灯（红）、路灯灯头（暖白）、信号灯（红/黄/绿三色组）、
楼体窗带（冷蓝）、公交站与广告牌灯箱。这样即使在大雾或阴天光照下，
城市街道的「灯火」层次依然成立。

### 10. 中文字体与字形范围

界面中文能正常显示的关键是**在 `ImGui::CreateContext()` 之后、后端初始化之前**
完成字体加载，并指定完整的中文字形范围（详见「三、中文字体说明」）。
字号切换通过 `io.Fonts->Clear()` → 重新加载 → `ImGui_ImplOpenGL3_DestroyFontsTexture()`
→ `CreateFontsTexture()` 重建图集实现，全程无需重启程序。

## 九、城市街景系统

### 9.1 为什么需要街景

只有车道线 + 沥青平面的场景，看起来像**实验跑道**而不是真实道路 ——
没有尺度参照，也没法直观判断「车开得快不快」。加入街景后：

- **提供尺度参照**：行道树高度约 5~8.5 m、楼高 8~60 m，与车辆形成真实比例
- **提供速度感**：两侧物体连续掠过是速度感知的主要来源
- **提供场景可信度**：路缘石、人行道高差让道路结构一目了然

### 9.2 道路横断面布局

道路为**双向 6 车道**，中央以双黄线分隔。所有坐标在
`adas.cpp` 顶部以常量集中定义（`kLaneCenterX` / `kRoadEdgeX` / `kCurbX` …），
渲染层（`drawGround`）与 BEV 层（`bev.cpp`）都引用同一套约定，
避免「改了一处忘了另一处」导致的错位。

```
 X = 0            双黄线中心（中央分隔带，宽 0.85 m，仅颜色区分）
 X = ±1.875       第 1 车道中心（最内侧）
 X = ±5.625       第 2 车道中心 ← 自车所在车道（lane 4，X = +5.625）
 X = ±9.375       第 3 车道中心（最外侧）
 X = ±13.1        路面外沿（含硬路肩）
 X = ±13.25       路缘石（宽 0.30 m，抬高 17 cm）← 关键视觉分界
 X = ±13.4~21.0   人行道（抬高 15 cm，浅灰水泥）
 X = ±14.2~19.4   行人活动带（行人来回散步范围）
 X = ±13.0        自行车道中心（骑行者所在）
 X = ±22~26.5     绿化带：行道树
 X = ±14.2~15    路灯（悬臂伸向车道）
 X = ±18.5~20    电线杆
 X = ±27~62       楼房退线区（越远离道路越高，形成「街道峡谷」）
```

> **X 符号约定**：`X < 0` 为对向车道（车辆朝 `-Z` 行驶），
> `X > 0` 为同向车道（车辆朝 `+Z` 行驶），符合右侧通行规则。

### 9.3 十六种道具

| 道具 | 构成 | 生成规则（沿 Z 轴） |
|---|---|---|
| **行道树** | 树干 + **3 层球状树冠**（下大上小、逐层变亮） | 每 10 m 一棵，高度 5~8.5 m 随机 |
| **楼房** | 裙楼 + 主体（含竖向壁柱）+ 女儿墙 + 楼顶设备间 + **自发光窗带** | 每 20 m 一栋，越远越高（10→78 m 渐进） |
| **路灯** | 灯杆 + 悬臂 + **自发光灯头** | 每 30 m 一根，悬臂朝路面 |
| **电线杆** | 细长杆 + 两道横担 | 每 50 m 一根 |
| **信号灯** | 立杆 + 横臂 + **红黄绿三色灯组（按路口相位切换）** | 每个路口四角各一根 |
| **公交站台** | 顶棚 + 四立柱 + 背后灯箱广告 | 每 130 m 一处 |
| **广告牌** | 双支架 + 大面板灯箱 | 每 170 m 一处 |
| **护栏** | 立柱 + 波形横梁 | 沿**中央分隔带**两侧连续排布（每 10 m 一段） |
| **灌木** | 2~3 个压扁球体成丛 | 概率性点缀 |
| **路边停车** | 复用轿车零件，颜色按 variant 稳定选取 | 概率性（约 14%），贴右路缘 |
| **路边行人** | 复用行人零件，身高 1.55~1.86 m | 概率性生成，**会沿人行道来回走动** |
| **骑行者** | 自行车 + 前倾骑手（含头盔） | 概率性（约 38%），沿自行车道骑行 |
| **斑马线** | 6~8 条白色条纹板 | 路口前后 + 路口左右各一条（共 4 条） |
| **停止线** | 单条白色实线 | 同向 3 条 + 对向 3 条，位于斑马线之前 |
| **路口铺装** | 一整块横向沥青板 | 每个路口一块 |
| **锥桶** | 真圆锥 + 反光带 | 由感知层按需生成 |

启动时约生成 **288 个道具**，其中行道树 62 / 楼房 32 / 路灯 22 / 行人 43。


### 9.4 无限延伸与稳定伪随机

街景跟随「无限道路」世界循环平移。关键在于**用坐标索引做种子的哈希函数**
而不是 `std::rand()`：否则每次世界归零，楼房和树都会重新生成不同的形状，
画面会出现明显跳变。采用 `hash01(spanIndex, salt)` 后，**同一位置永远得到
同一栋楼、同一棵树**，世界平移在视觉上完全无感。

### 9.5 密度可调

主面板「街景密度」滑块（0.3x ~ 2.0x）改变沿 Z 轴的分段跨度，
调大即街道更密。密度变化时调用 `AdasWorld::rebuildStreetNow()`
重建整条街道，因此连远处已有的道具也会一起变疏密。

## 十、BEV + 占据栅格可视化（特斯拉 FSD 风格）

### 10.1 为什么需要 BEV

前向 3D 场景回答的是「**驾驶者看到什么**」；
而自动驾驶真正做决策的空间是「**以自车为中心的俯视栅格**」，也就是 BEV。

- 前向视图里，侧后方的目标根本不在画面内；BEV 里它们是可见的
- 前向视图有透视缩短，**距离开不准**；BEV 是等比例俯视，距离可直接读
- 规划算法（避障 / 换道 / 让行）天然工作在 BEV 空间，而不是图像空间

特斯拉车机上那块「俯视小地图 + 彩色方块车流」就是 BEV 可视化。
本项目复刻了它的四类形态与核心图层。

### 10.2 四类布局（F4 开关 · F5 循环）

| 布局 | 形态 | 对应真实场景 |
|---|---|---|
| **全屏 BEV** | BEV 铺满画面，3D 完全不画（省掉全部 3D 开销） | 停车 / 低速 / 查看全局态势 |
| **画中画 BEV** | 3D 主画面 + 右下角 BEV 小地图 | 特斯拉行驶中最常见的形态 |
| **上下分屏** | 上半 3D、下半 BEV | 调试：同一时刻对比两套视图 |
| **BEV 主画面** | BEV 铺满 + 右下角 3D 小窗 | FSD v12 车机界面 |

3D 视口与 BEV 视口在**同一张离屏 FBO**上通过 `glViewport` + `glScissor`
分区渲染，因此没有额外的帧缓冲开销。

### 10.3 占据栅格（Occupancy Grid）

栅格是两块等大的 `float` 数组，上传为 **`GL_R32F` 单通道浮点纹理**：

| 通道 | 语义 |
|---|---|
| `occupancy[]` | 该格被障碍占据的程度 `0~1` |
| `drivable[]` | 该格是否在道路（含路口）范围内 `0` / `1` |

**为什么用 `GL_R32F` 而不是 `GL_R8`**：占据值需要保留低位差异
（预测轨迹的弱占据只有 0.05~0.15），量化到 0~255 会被直接截断成 0，
热力图的色阶也会出现可见台阶。

光栅化策略：不做通用多边形填充，而是取目标 OBB 的 AABB 范围、
**逐格判断格心是否落在旋转矩形内**。单个目标最多检查 ~24×24 格，
几十个目标的总开销可忽略，代码量却远小于扫描线填充，且天然支持旋转。

各类目标有**不同的膨胀半径与危险权重**：

| 类别 | 膨胀半径（m） | 危险权重 |
|---|---|---|
| 卡车 | 0.45 | 1.00 |
| 轿车 | 0.30 | 0.92 |
| 骑行者 | 0.28 | 0.80 |
| 行人 | 0.25 | 0.74 |
| 锥桶 | 0.10 | 0.55 |

### 10.4 可行驶区域（Drivable Space）

由「所有车道 ∪ 路口铺装区」构成，**不含**人行道、绿化带、建筑占地。
BEV 引擎按自车朝向旋转后逐段铺进栅格，因此 `lockToEgo` 打开时
可行驶区域会跟着自车一起转。

### 10.5 自研风险色阶

`occupancy.frag` 用的是**自己写的单调色阶**，
而不是常见的 `jet` / `rainbow`。原因：

- **彩虹色阶非单调** —— 中间那段蓝色在视觉上「看起来很安全」，
  但它其实代表中等风险，容易读错
- **对色盲不友好** —— 红绿相邻难以区分

本项目采用「透明 → 青 → 青绿 → 琥珀 → 橙红 → 饱和红」的单调递增色阶，
**亮度与危险程度单调相关**，任何色觉条件下都能读出风险顺序。
透明度也随占据值递增：弱占据几乎透明（露出底下的道路），
强占据完全不透明。

### 10.6 BEV 图层清单

| 图层 | 内容 | 快捷键 |
|---|---|---|
| 占据栅格热力图 | 目标 OBB + 预测轨迹（沿速度外推 1.5 s，渐隐） | `O` |
| 可行驶区域 | 青色半透明底 | `D` |
| 车道拓扑 | 车道线折线 | 面板 |
| 目标框 + 速度矢量 | 带朝向矩形 + 速度箭头（长度 ∝ 车速） | 面板 |
| 传感器覆盖 | FOV 投影到地面（圆 / 扇形） | 面板 |
| 米格网 | 每 10 m 一条，50 m 整倍数更亮 | 面板 |
| 自车轮廓 | 白色矩形 + 车头三角箭头 | 常显 |
| 规划轨迹 | 青色线 | 面板 |

### 10.7 性能预算

占据栅格在 CPU 端重建，因此**必须盯着耗时**。主面板
「BEV 栅格统计」实时显示重建耗时与「占 60fps 预算百分比」，
超过 25% 会变橙提示。

可调的两个杠杆：

- **栅格分辨率**（0.20 ~ 2.00 m/格）—— 0.5 m + 120×80 m 视野 ≈ 19200 格
- **更新间隔**（每 1~8 帧重建一次）—— 视觉上几乎无差别，开销线性下降

### 10.8 与 3D 视图的一致性约束

BEV 里画的预测轨迹与占据栅格里的「未来占据」**必须用同一套外推参数**
（沿速度方向 0.3 s × 5 点 = 1.5 s），否则会出现
「线画在一处、热力图在另一处」的矛盾观感。
这一点在 `bev.cpp` 与 `renderer.cpp` 里都以注释显式约束。
